### One shared starter (acceptance criterion `shared-environment`)

Today `run-web.ts` does containers + DB reset + API build + web export, and
`playwright.config.ts`'s `webServer` starts the fixture server, the API and
the static server. Maestro has no `webServer`, so the starting moves into
one function both runners call:

```ts
// env/environment.ts
export interface E2eEnvironmentOptions { web: boolean }
export async function withE2eEnvironment(
  options: E2eEnvironmentOptions,
  run: () => Promise<number>,
): Promise<number>;
// startContainers → resetE2eDatabase → `pnpm run build` (API)
// → [web: buildWebApp] → spawnService(fixtures) → spawnService(api)
// → [web: spawnService(static)] → run() → stop services (reverse) → stopContainers
```

The fixture-server and API service definitions (command, guard preload,
`cwd` `apps/e2e` so `apps/api/.env` is never loaded, `buildApiEnv()`) move
verbatim from `playwright.config.ts` into `environment.ts`; nothing is
copied. Playwright keeps `checks/environment.spec.ts` as its first project.
Proof the refactor is neutral: two green `pnpm e2e:web` runs before any
Maestro work (22 passed / 1 skipped, as at slice 01's close).

### How the app reaches the API: the dev build loads its JS from an e2e Metro

The dev build (`expo-dev-client`, EAS profile `development`,
`APP_VARIANT=development`) carries no JavaScript: it loads the bundle from
a Metro server. `EXPO_PUBLIC_API_URL` is read in `src/api/client.ts` and
inlined **by Metro at bundle time**, not baked into the binary. So:

- `env/metro.ts` starts `pnpm exec expo start --dev-client --port 8183
  --localhost --clear` in `apps/mobile`, env `EXPO_PUBLIC_API_URL=
  http://localhost:3101`, `EXPO_PUBLIC_APP_ENV=e2e`, `APP_VARIANT=
  development`, `CI=1` (non-interactive). Ready on
  `http://localhost:8183/status` = `packager-status:running`; then one GET
  of the iOS bundle to warm it, so the first flow does not time out.
  Port 8183 is distinct from the dev Metro (8082). `--clear` keeps a bundle
  inlined with the dev URL from being reused; the process env wins over
  `apps/mobile/.env` (Expo's env loader never overrides).
- The simulator shares the host network, so `localhost:3101` from the app
  is the e2e API. Native fetch is not subject to CORS, so `CORS_ORIGIN`
  stays the web origin.
- `common/launch.yaml`: `launchApp {appId: com.bspot.mobile.dev,
  clearState: true}`, then `openLink:
  bspot-dev://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8183`
  (the dev client's own "open this server" link), wait for the tab bar,
  and tap "Continue" on the dev-menu onboarding sheet when it shows
  (`runFlow when visible`). `clearState` wipes the app container: local
  history (AsyncStorage) and the cookie jar, so each flow starts logged out
  with an empty history.

### Deep link with the dev scheme

The dev build answers `bspot-dev://` (`app.config.ts`), not `bspot://`.
Expo Router maps `bspot-dev://company/602018897` to `app/company/[id].tsx`.
The scheme comes from `e2e-env.ts` (`DEV_SCHEME`) through `-e`, never
written in a flow.

### Values in the flows come from TypeScript

`run-mobile.ts` calls `maestro test maestro/flows --config
maestro/config.yaml --format junit --output maestro-results/report.xml
--debug-output maestro-results/ -e KEY=VALUE…`, with `buildMaestroEnv()`
providing every value a flow needs: API, control and dev-client URLs, the
scheme, the e2e emails (`E2E_USERS`), and the catalogue values
(`KNOWN_FOOD`, `FERRERO_FIXTURE`, `UNKNOWN_BRAND_PRODUCT`…) from
`fixtures-server/catalogue.ts`. No port, email or fixture name is typed in
YAML. The run's exit code is Maestro's.

### Control server: the test's hands outside the app

Maestro's `runScript` can only make HTTP calls. Database writes and the
MailDev lookup already exist in TypeScript (`support/db.ts`,
`support/maildev.ts`); a small HTTP front, served from inside the
`run-mobile` process on `127.0.0.1:4011`, exposes them so nothing is
rewritten in JavaScript:

| Route | Calls |
|---|---|
| `POST /reset` | `resetMutableState()` |
| `POST /sessions/expire {email}` | `expireSessionsOf(email)` → `{count}` |
| `POST /admins/revoke {email}` | `revokeAdminRole(email)` |
| `GET /magic-link?email=&since=` | `fetchLatestMagicLink(...)` → `{link}` |
| `GET /suggestions?notes=` | `findSuggestionsByNotes(notes)` |

It lives in `apps/e2e` and the API never knows it (same standing as the
fixture server and the fetch guard). Suggestions for moderation are
created through the API's public `POST /api/brand-suggestions`, as on web.

### Clean state between flows

Every flow has `onFlowStart: [runFlow: ../common/reset.yaml,
runFlow: ../common/launch.yaml]`: database back to the seeded state
(`/reset`, same function as the web `beforeEach`), app data wiped by
`clearState`. Flows run one at a time, in the order of `config.yaml`
(`executionOrder.flowsOrder`, `continueOnFailure: true` so one red flow
still lets the others report).

### Session expiry, server-side

Same mechanism as web: `POST /sessions/expire` moves `expiresAt` into the
past; the next `/api/admin/*` call answers 401 and the existing
`QueryCache.onError` in `app/_layout.tsx` toasts "Votre session a expirée.
Reconnectez-vous." and `router.replace('/login')`. Flow: logged in, Admin
tab → counter → suggestions screen, expire, tap `suggestions-tab-approved`,
assert the toast text and `login-email-input`, then back to the Scanner
tab: `nav-login-link` reads "Se connecter" and `nav-admin-link` is absent.
(Blocked by the login finding below.)

### The dev build (needs the human, once)

Two ways, both producing `com.bspot.mobile.dev` with scheme `bspot-dev`:

- **Local (recommended):** `cd apps/mobile && APP_VARIANT=development
  pnpm exec expo run:ios --device "iPhone 17 Pro Max"`. No account, no
  signing for a simulator; `expo prebuild` writes `apps/mobile/ios/`
  (ignored), `pod install`, then an Xcode build (10–20 min the first
  time). Rebuild only when a native dependency changes.
- **EAS:** `eas build --profile development --platform ios` (simulator:
  true in `eas.json`), needs `eas login` on the `tat-lonestone` account,
  queue time; then `eas build:run` installs it.

### Decisions the spec left to the implementation

- One starter for both runners (`withE2eEnvironment`), Playwright's
  `webServer` removed, rather than a second list of processes.
- The dev client loads its JS from an e2e Metro on 8183 with the e2e API
  URL; the binary is the plain `development` build.
- Database and MailDev actions go through a control server inside the
  runner process (port 4011), reusing `support/db.ts` and
  `support/maildev.ts`; Maestro scripts stay one-line HTTP calls.
- Every value a flow uses is passed with `-e` from `e2e-env.ts` and
  `catalogue.ts`.
- Per-flow reset: `/reset` + `clearState` in `onFlowStart`.
- Brand suggestion reached through its own route's deep link, the same
  bypass of the camera the spec chose for the company page.

## Findings that contradict the spec

### Native magic-link login cannot log the app in (blocks 4 iOS rows)

Fact, from the code: the session is a Better-Auth cookie
(`apps/api/src/modules/auth/auth.config.ts`), the app sends it with
`credentials: 'include'` (`apps/mobile/src/api/client.ts`). On iOS that
cookie lives in the app's own cookie jar. `signInMagicLink` sends no
`callbackURL`, so the link the email carries is
`http://localhost:3101/api/auth/magic-link/verify?token=…&callbackURL=/`;
whatever opens it — Safari, Mail, Maestro's `openLink` — sets the cookie
in **Safari's** store and redirects to the API root. The login screen's
3-second session polling then still gets `null`. Web works only because
browser tab and app share one cookie jar. Not yet confirmed on a device
(no dev build installed); the first flow run will confirm it.

Rows blocked as written: magic-link login, admin entry (admin side and
demoted admin), moderation, expired session.

Options:
- **A. Fix native login in its own task, first** (recommended): e.g.
  `@better-auth/expo` (server plugin + client with `expo-secure-store`,
  callback `bspot://…`), or a deep-link callback that the app verifies
  with its own fetch. A real user bug, fixed for users; the four flows are
  written on top of it.
- **B. Inject the session cookie into the simulator's app container**
  (`Library/Cookies/Cookies.binarycookies`) from outside. Green flows over
  a path no user takes; hides the bug. Not recommended.
- **C. Drop the four iOS rows.** Loses the coverage the task exists for.

Meanwhile slice 02 can deliver everything else (environment, Metro,
control server, scan, brand suggestion, history, logged-out admin entry)
and add the auth flows once A lands.

Side note for A: Better-Auth's origin check rejects cookie-carrying POSTs
with no `Origin` header (native `fetch` sends none), so native sign-out
would answer 403 in production; under `NODE_ENV=test` the check is
skipped, so e2e would not see it.

### History cannot be written without the camera (changes one iOS row)

Fact: only `useBarcodeScanner` writes the history
(`src/features/scanner/hooks/useBarcodeScanner.ts`, `addEntry`), and on
native it is fed only by the camera. The company deep link does not write
history; the simulator has no camera. So "History lists what was just
looked up" cannot be walked on iOS.

Options:
- **A. Seed the history from outside** (recommended): before launch, the
  runner writes the entry into the app's AsyncStorage manifest in the
  simulator container (`Library/Application Support/com.bspot.mobile.dev/
  RCTAsyncLocalStorage_V1/manifest.json`, key `@b-spot/scan-history`),
  like the database seed. The iOS flow checks the empty state, the list
  and the tap to the company page; the write side stays covered by the
  web journey, which runs the same hook.
- **B. iOS row covers only the empty state.**
- **C. Drop the iOS row.**
