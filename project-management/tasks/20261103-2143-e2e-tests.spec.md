**Status:** ready

## Context

`main` has not moved since January: pull request #12
(`feat/user-auth-admin-ui`) carries the whole app built since — scan,
company page, history, brand suggestions, magic-link login, admin
moderation. The only automated coverage is unit tests and one API e2e test
in Jest; the full login → admin flow has never been checked end to end
(the polish step of the archived `speckit-user-auth-admin-ui` tasks left it
manual). Before merging #12, the critical journeys need a safety net that
runs through the real app, the real API and a real database: Playwright
on the web build first, then Maestro on the iOS app.

## Scope

**Included:**
- One e2e test per critical journey (list below), on the web build with
  Playwright, then on the iOS simulator with Maestro.
- A local e2e environment that one command brings up: a dedicated test
  database, seeded; the API; the web build; MailDev; a local fixture server
  standing in for the four external APIs.
- The four external API base URLs (Open Food Facts, Open Beauty Facts,
  recherche-entreprises, Pappers) made configurable, today's URLs staying
  the defaults.
- Stable test selectors (`testID`) on the elements the journeys touch.
- (added 2026-11-03) The fix of the Open Beauty Facts fallback: a 404
  from Open Food Facts means "not found" and falls through to Open Beauty
  Facts, with a regression test.

**Not Included:**
- CI: the suites run locally, by hand, before a merge. A CI task comes
  later.
- Android: Maestro targets the iOS simulator only.
- The camera itself: on mobile the scan journey starts from the company
  page deep link; scanning a real barcode stays a manual check.
- Exhaustive coverage of every acceptance scenario of the archived Spec
  Kit specs: one test per journey, its main path and the failure that
  matters most.
- Any real call to an external API during a run — Pappers quota included.

## Acceptance Criteria

- [ ] **every-journey-covered** — each row of "The critical journeys" has a
  passing test on each platform the row marks.
- [ ] **no-external-network** — a full run with outbound network to the
  four external API hosts blocked passes.
- [ ] **default-urls-unchanged** — with no e2e variables set, the API calls
  the same four external URLs as before this task.
- [ ] **one-command-web** — `pnpm e2e:web` from the repo root, with Docker
  running, brings up the environment, runs Playwright and exits non-zero
  on any failure.
- [ ] **one-command-mobile** — `pnpm e2e:mobile`, with a booted iOS
  simulator and the dev build installed, runs the Maestro flows and exits
  non-zero on any failure.
- [ ] **dev-data-untouched** — a run never writes to the development
  database: it uses its own database, reset at the start of each run.
- [ ] **repeatable** — two consecutive runs both pass, with no manual step
  between them.
- [ ] **suite-green** — `pnpm lint`, `pnpm test`, `pnpm build` pass.

## Seams

- **External API base URLs** — the API reads each of the four base URLs
  from its environment; unset, it uses today's URL.
- **Fixture server** — answers the four external APIs' routes the API
  uses, for a fixed catalogue of barcodes, brands and SIRENs; anything else
  gets the "not found" answer of the real API.
- **E2E environment** — one entry point that resets and seeds the test
  database (admin user, brands, the catalogue's companies), starts the
  fixture server, the API and the web build, and tears them down.
- **Magic link from MailDev** — a helper that, given an email address,
  returns the latest magic link MailDev received for it, through MailDev's
  REST API.
- **Stable selectors** — the `testID` of each element a journey touches;
  React Native Web renders it as `data-testid`, so the web and iOS suites
  share the names.

## Implementation Decisions

- **Real stack, fake outside world.** Nothing inside the app is mocked:
  the browser and the simulator talk to the real API and database. Only
  the four external APIs are replaced, at the network boundary.
- **Configurable URLs, not an e2e mode in the code.** The API learns no
  "test mode": it only reads four optional base URLs. No test-only branch
  ships in the API or the app.
- **No test code in the app.** On mobile the camera is bypassed by the
  existing company route through its deep link, not by a dev-only input.
- **Own database.** The e2e environment uses a separate database name on
  the same Postgres container, recreated from the migrations and seeders
  at each run.
- **Session expiry** is produced from outside the app (session removed or
  invalidated server-side), never by a hook added for the test.

## Testing Strategy

- The journeys are the tests. Each one starts from a clean, seeded state
  it does not share with another journey's writes.
- The URL configuration gets a unit test in the API's Jest suite
  (defaults kept, override read).
- The fixture catalogue is small and named: one known food product, one
  known cosmetic, one product with an unknown brand, their companies.
